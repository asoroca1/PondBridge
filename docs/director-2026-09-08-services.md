# PondBridge third-party services inventory

**Audit date:** 2026-09-08  
**Scope:** repository and checked-in deployment/configuration evidence at the current release tree, plus official vendor pricing/limit pages.  
**Evidence rule:** a code/config reference proves intended integration, not that an account is connected, paid, healthy, or using the declared values. Historical audit documents are context only and are not live proof.

## Executive findings

The source has seven runtime provider families: Cloudflare (DNS, Pages/static web, R2, optional Stream), Render (declared API host), Supabase (Postgres/Data API), Clerk (auth in the production blueprint, with legacy/hybrid fallback still supported), Stripe (billing), Resend (email), and OpenAI (AI features). Apple APNs and Firebase FCM are implemented as optional mobile delivery paths. GitHub is the source/CI control plane, with a checked-in workflow and current authenticated CI evidence; hosted database steps remain skipped because repository variables are absent.

Render is the only backend host declared in the production Blueprint (`render.yaml`, `plan: starter`); `fly.api.toml` and `vercel.json` are checked-in alternatives and should be treated as dormant until an account and DNS cutover are evidenced. Cloudflare Pages is proven live: the `pondbridge` deployment is healthy at head `2fd23b5`. Cloudflare Stream is documented and implemented, but its credentials are absent from `.env.example` and its use is optional/fallback-safe.

No checked-in file proves current vendor plan, account owner, billing method, usage, quota headroom, domain verification, webhook registration, backup/PITR posture, or connector availability. The parent audit should collect those from provider dashboards/connectors and attach dated exports or screenshots.

The parent task supplied a small set of live observations for this audit: one active Render `pondbridge-api` Starter service (0.5 CPU/512 MiB), `/health`, and checks-pass auto deploy from `main`; four legacy Render services are suspended. Resend reports the `pondbridgealumni.com` domain verified in `us-east-1`, sending enabled, tracking off, and an expected enabled webhook. GitHub `main` CI is green, but hosted database gates are disabled because repository variables are absent. These observations are called out as parent-supplied live evidence, not inferred from source.

The confirmed growth envelope is 10–20 camps with 300–600 members each: approximately 3,000–12,000 registered members. The parent’s current live checks also show 470 registered Clerk users (this is a user count, not measured monthly retained users), a healthy Cloudflare Pages `pondbridge` deployment at head `2fd23b5`, and a Cloudflare zone on the Free Website tier. Cloudflare account subscription/zone-settings reads returned 403, so those checks do not establish the complete account subscription or billing picture. A one-hour Render sample showed CPU max 0.126 cores of 0.5 (25.2%) and memory max 144,629,760 bytes of 512 MiB (26.9%); no latency series was available, so this is a limited snapshot rather than a capacity guarantee. Stripe live charges and payouts are enabled, but the current enabled webhook shape/date (`2026-01-28.clover`) is under investigation against the app’s pinned Stripe API version and should not yet be called healthy.

## Scale planning for the confirmed envelope

The member count alone does not determine email volume. If directors send 1–4 broadcasts per member per month, the 3,000–12,000-member envelope implies a planning range of roughly 3,000–48,000 broadcast-recipient emails per month, before verification, invite, digest, bounce, and other transactional messages. This is a scenario range, not observed sending. It places the low end at Resend’s Free monthly quota and puts the high end near the current Pro 50,000-email monthly inclusion; any transactional traffic or retries can cross that boundary. Before launch, record actual recipients and sends per camp, set a quota alert below the selected tier, and confirm whether broadcasts are personalized/batched because each recipient counts separately under Resend’s quota rules.

For 10–20 camps, retain a single canonical Render API service and Cloudflare Pages web deployment while adding measured headroom checks. The sampled 25% CPU and 27% memory maxima show no immediate pressure, but the missing latency series, concurrency, database connections, R2/egress usage, and peak-period sample prevent a scale decision. Capture p95/p99 latency, event-loop saturation, concurrent sockets, Supabase connections, and Render memory/CPU during a representative multi-camp rehearsal before changing compute tiers. The current Render Starter should be reconsidered when sustained peak CPU or memory approaches 70–80%, p95 latency rises, or connection limits are reached; these are operational guardrails for review, not vendor plan limits.

At 3,000–12,000 registered members, Clerk’s 470-user observation is well below the forecast but cannot be compared directly with Clerk’s MRU billing unit. Track registered users, monthly retained users, sign-ins, and auth 429s separately. For Supabase, measure database size, pooled/direct connections, egress, storage, Realtime messages, and backup/PITR state across all camps; project count and compute cost can grow independently of member count. For R2 and Stream, alert on object storage, Class A/B operations, stored minutes, and delivered minutes rather than assuming media usage scales linearly with members.

The lowest-cost scale path is to keep the healthy Cloudflare Pages Free deployment and the single Render Starter service while traffic remains within the measured headroom, add quota alerts and peak rehearsal first, and avoid provisioning Fly/Vercel in parallel. For email, use Resend Free only when actual combined transactional plus broadcast volume stays below 3,000/month; otherwise the next predictable step is the published Pro tier rather than relying on overage or a daily-limit failure. For media, keep large assets in R2 and enable Stream only for clips that need cross-browser transcoding. Scale Render or Supabase after the measurements above identify the limiting resource, so a paid compute increase addresses a demonstrated bottleneck.

## Improvement opportunities grounded in code

1. **Make one deployment authority explicit.** Add a short release decision that Render + Cloudflare Pages are canonical and mark Fly/Vercel files as archived examples, or add a tested failover runbook. Today three deploy descriptors can be mistaken for three active control planes (`render.yaml`, `fly.api.toml`, `vercel.json`).
2. **Close the Cloudflare Stream contract.** Add Stream-specific variables to `.env.example` and `render.yaml` (`CLOUDFLARE_STREAM_API_TOKEN`, webhook secret, enabled flag) and expose a readiness check. `cloudflareStream.js` currently falls back to the broader Cloudflare token as documented in `docs/CLOUDFLARE_STREAM.md`; least privilege and webhook health should be visible in preflight.
3. **Turn provider ceilings into telemetry.** Export counters/alerts for R2 bytes/operations, Stream stored/delivered minutes, Resend quota/429s, Stripe 429s/webhook lag, Supabase DB/egress/connections, Clerk 429s, and OpenAI budget denials. Existing operational telemetry (`apps/api/src/services/operationalTelemetry.js`) and provider services are the natural integration points.
4. **Separate product guards from vendor quotas.** Publish the source guards (`R2_MAX_UPLOAD_BYTES`, `EMAIL_BROADCAST_MAX_RECIPIENTS`, OpenAI monthly budgets, token/timeouts) beside vendor quotas in readiness output so operators do not mistake a local cap for a purchased plan limit.
5. **Add an account-evidence checklist to deployment preflight.** Extend `docs/DEPLOYMENT.md` / `apps/api/scripts/dbPreflightCheck.js` with dated checks for verified Resend domain, Stripe webhook delivery, Clerk authorized parties, Cloudflare zone/Pages/R2/Stream IDs, Render service/plan, Supabase PITR/spend cap, and APNs/FCM key age. The check should report `unknown` when connector evidence is unavailable rather than infer health from non-empty environment variables.
6. **Protect the AI spend boundary.** The OpenAI service ledger and budgets are good application controls, but `render.yaml` currently enables several model variables while `SUPER_COPILOT_ENABLED=false`. Keep all AI features behind explicit rollout flags and reconcile application cost records with the OpenAI project usage dashboard before enabling a new camp cohort.
7. **Complete mobile release evidence before enabling push.** APNs and FCM code paths can silently remain unconfigured. Add a signed iOS/TestFlight and Android internal-track smoke test, token expiry cleanup, and delivery-failure counters before advertising push as available.

## Coverage gaps and requested live evidence

The source audit cannot establish current account truth for: provider account owner and MFA; complete Cloudflare subscription/billing settings (some account reads returned 403); current usage and quota headroom; Pages/Render settings beyond the parent’s sampled checks; Supabase PITR/backups and spend cap; Stripe live/test mode and whether the current webhook shape matches the pinned SDK/API contract; Resend domain reputation, actual send volume, and complaint rate; Clerk app/environment and MRU; OpenAI organization spend/rate tier; Stream webhook subscription; APNs/FCM signing and production delivery; GitHub branch protection, Actions billing/minutes, and deploy/secret-scanning policy; or whether Fly/Vercel are still retained.

For each active provider, the parent audit should capture provider name, account/project/service ID, environment, plan, billing owner, usage date range, quota/limit, current value, alert threshold, and evidence URL/export. A blank secret, a checked-in example, or a historical document is not evidence of connection or plan.
