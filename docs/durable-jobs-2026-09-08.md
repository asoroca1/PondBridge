# Durable immediate broadcasts and Clerk acknowledgment

Immediate director broadcasts can enqueue up to 5,000 recipients when `DURABLE_JOBS_ENABLED=true`. Scheduled broadcasts and invitation requests retain their existing provider scheduling and size limits. Questionnaire imports retain the separately tested bounded concurrency implementation; they are not yet durable jobs. The queue does not offer cancellation.

Apply `supabase/migrations/20260908220000_durable_tenant_jobs.sql` before enabling the flag on API processes. The existing API process starts and drains the worker; no separate scheduler is required. Use Resend in production. Mock mode supports rehearsals without messages. SMTP is deliberately unsupported for durable sends because the transport cannot guarantee retry idempotency. Integrate the email service's `requireUnchangedRecipients` option before enabling: its final suppression check must throw `EMAIL_RECIPIENT_SET_CHANGED` before provider calls if any supplied recipient has become suppressed.

Every tenant job is bound to the authenticated actor, a client request key and content fingerprint. Service-only SQL rejects tenant/actor mismatch and conflicting replay. HTTP retries return the existing job even after the original payload is scrubbed. Composer storage contains opaque keys, SHA-256 content fingerprints and progress, never email bodies or audiences. Tenant-scoped status polling resumes after reload. Queued acknowledgment means accepted for processing, not delivered or inbox placement.

Workers claim at most one bulk chunk per second across replicas. Each chunk has at most 40 recipients, a 90-second lease and 20-second heartbeat. Active tenant, actor membership/role and super-admin allowlist are rechecked. Preferences, suppression and contact holds are checked again before delivery. Lookup errors fail closed. Before a provider call, the worker persists exact personalized messages, unsubscribe headers and sender. Encoded preparation is capped at 5 MB and SQL state at 6 MB. The same chunk reuses its provider idempotency key. Provider mode, account hash, endpoint, batching settings and implementation contract are frozen; changes after an uncertain attempt require review. Changed eligibility after an uncertain attempt also stops automatically rather than reindexing provider keys. Partial acceptance preserves known counts and requires review.

Three attempts per chunk and a 23-hour job expiry bound retries below Resend's 24-hour idempotency retention. A worker crash releases no acknowledgment; an expired lease allows another worker to resume. Successful work immediately removes its payload; expiry removes any retained payload and prepared messages. Aggregate status and non-content request hashes remain for replay detection. An API shutdown may outlive its 25-second graceful drain and leave a lease for recovery; this is safe because prepared provider requests reuse their keys.

Rollback: disable `DURABLE_JOBS_ENABLED` and restart all API workers, allowing any in-flight call to finish or its lease to expire. Keep the migration/data for inspection; disabling the flag pauses queued work rather than cancelling messages already accepted by the provider. Never manually replay a failed uncertain job with a new key. Review provider acceptance and the job's counts first. Jobs past expiry cannot resume.

Validation: 21 focused safe API tests passed (8 queue + 13 Clerk), including 600 synthetic recipients in exactly fifteen bounded chunks, stable request replay after connection loss, transport/eligibility changes, partial acceptance, authorization, and lost leases. Disposable local PostgreSQL tests passed six groups covering grants, cross-tenant rejection, conflicting keys, concurrent replica claims, lease/cursor compare-and-set, and expiry/scrubbing. Reproduce with `python3 apps/api/tests/durableJobs.local.py`; it creates and removes only a unique fixture database in the local Supabase Docker container. API/web lint passed (two existing API warnings); production web build passed. No real messages or hosted writes were performed. Mocked timing is not hosted delivery throughput.

Clerk `email.created` code dispatch retains signature verification and tenant resolution and waits for the email provider's acceptance before returning success. Provider failure reaches Clerk for retry; expired code events are ignored. OTP plaintext is not persisted. Provider acceptance is distinct from inbox delivery.

Vendor contracts: [Clerk webhook retries](https://clerk.com/docs/guides/development/webhooks/syncing), [Clerk event timestamps](https://clerk.com/docs/guides/development/webhooks/overview), [Resend idempotency](https://resend.com/docs/dashboard/emails/idempotency-keys).
